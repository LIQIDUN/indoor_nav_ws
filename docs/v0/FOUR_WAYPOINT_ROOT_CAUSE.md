# 四航点准备悬停超时：证据与修复边界

## 现象不能混淆

- 历史最终提交 `a07623f` 的 `20261026T182532-multi`：准备悬停超时，导航IDLE、尚未start。
- 恢复后原最终生产源码的全新实例 `20261026T193632-multi`：**原准备门槛通过**，第四点附近因POSE_STALE锁存FAIL，属于另一类故障，不能写成四点通过。
- 修改后的冷启动 `20261026T210621-single`、`20261026T210836-multi` 已有通过记录；后续最终源码重复结果由总矩阵索引，不用早期PASS覆盖失败。

## 根因证据链

目标固件源码为 `/home/liqidun/github/ardupilot@2a3dc4b7bf2507120f7378a7b2fde73185e0c325`（Copter4.5.7）。`ArduCopter/mode_guided.cpp` 的 `do_user_takeoff_start()`：无健康测距地形分支时，把takeoff高度解释为 **ABOVE_HOME**，再转换为 **ABOVE_ORIGIN**。测试驱动发送1.0m，原准备条件却直接检查Gazebo世界真值Z>0.85m，二者并非无条件共享同一绝对零点。

历史实例 `.sitl_runtime/v0/20261026T181944-3520869` 连续用于最终单点和最终四点，DataFlash原始文件仍保留。独立标准库离线读取结果在 `evidence/resume_audit/historical_altitude.json`：

| 时间/记录 | 数值 |
|---|---|
| EKF origin，ORGN Type0 | 583.99m |
| 第一次ARM时home，ORGN Type1 | 583.96m |
| 第一次起飞对应EKF目标 | 约0.97m；单点通过 |
| 第二次ARM前CTUN Alt | 约-0.128m；上一轮刚结束LAND/DISARM |
| 第二次ARM时home，ORGN Type1 | 583.86m |
| 第二次1m ABOVE_HOME → ABOVE_ORIGIN | `1 + 583.86 - 583.99 = 0.87m` |
| 第二次超时前CTUN DAlt / Alt | 约0.8700m / 0.8595m |
| 同次telemetry真值最高Z | 0.83423m，低于驱动0.85m绝对门槛 |

因此，这次高度平台不是“飞控被命令去EKF1m却只到0.83m”的证据。飞控实际目标约0.87m，跟踪约0.86m；另有EKF与Gazebo的高度偏差。准备判据在复用实例后的高度基准改变下不再等价于“达到1m相对home并稳定”。

以上直接证明home/高度基准错配与实例复用有关；**不进一步声称已因果定位所有着陆后EKF/气压高度偏差的物理来源**，也不把它归为导航节点故障。导航从未开始，不能通过改航点算法解决该准备失败。

## 最小修复

1. 不改1.0m起飞指令，不降低0.85m真值门槛，不放宽0.06m/s速度范数门槛，不延长35s悬停准备超时。
2. 每个正式案例创建全新runtime/EEPROM；`flight_claim.json` 用独占创建禁止第二次飞行复用同一实例。地面状态仍须核验DISARM、GPS/EKF、参数及稳定悬停。
3. 在独立冷启动runner等待Master/路由，并在驱动内等待身份与SIM参数实际就绪；不能把roslaunch已启动当参数已下载。此前一次批测在SIM参数未就绪时拒绝，原日志保留。
4. 每例保存准备telemetry、home高度、源码/YAML/SITL参数哈希、阶段标签与退出结果，区分前置失败、准备失败和任务执行失败。
5. 停止工具把已核验启动器的zombie视为已退出，由其父runner回收，避免“子进程已停、父runner等待stop、stop又等父runner回收”的误报。此修复不涉及飞行控制。

## 修复不能证明什么

冷启动消除的是正式测试的复用状态与基准混淆，不是对真实飞机高度精度的认证。真实任务P0仍捕获飞手悬停时的EKF Z，z=0不代表地面。后续若需专门评估连续多架次、复用实例或世界绝对高度，应另立清楚的home/origin/真值参考对比，不套用本次PASS。

原源码冷启动后的POSE_STALE FAIL也完整保留；没有放宽0.35s pose门槛。后续通过不等于定位所有偶发调度/遥测中断原因，持续时效监测与故障锁存仍是必须保留的保护。
